# 提示词版本索引

用途：回答"**哪一版改了什么、为什么改、验证没验证**"。每次运行都会把实际用到的提示词快照进
`runs/<run>/metadata/prompts/`，并在 `run.json` 里记录路径与 sha256；本索引补上人类可读的变更说明。

维护规则：

1. 改提示词 = 新建版本文件，**不修改历史版本**；
2. 新建版本时必须在下面补一行，四个要素写全：变更、为什么、验证、状态；
3. 同一时间每个角色只有一版标"当前"，必须与 `config/vlm-providers.json` 一致；
4. 还在试、没验证的思路先用草稿文件试，**验证通过后再冻结版本号**，避免版本号膨胀。

**样本 B：两页关键页各 3 轮复跑**

| 页面 | 3 轮 body_changed | 判定 |
| --- | --- | --- |
| 化学 2304985123882770867:2 | true / true / true | 稳定命中 |

**样本 C：像素剖面实测（作为真值）**

化学 `2332243692174590286:7`，框 `y=[0.905,0.925]` → 像素 y[1587,1622]；正文末行墨迹在 y=1572–1591。
即**框确实切掉正文末行约 5 像素**，该页确为伤正文；VLM 三轮均判 clean，属漏报。

**结论**

- `body_changed` 对大切口（≥10px）稳定命中；对 5 像素级切口超出 VLM 分辨能力，无法仅靠提示词稳定识别。
- 漏报不会造成误交付：该页被 Java 门禁拦下，始终进人工审核、从不交付，正文红线未被突破。
- 业务侧建议：**凡 `manual_review` 一律保持原图**，把 `gate_audit=body_damaged` 当辅助提示，而非唯一依据。

### v13 合成样本识别率实测（2026-09-18）

做法：以真实试卷页为底图，用脚本故意制造不同类型的正文伤害，再单独调用 `audit` 判定，
每个样本重复 3 轮。样本与脚本产出在 `/tmp/audit_synth`，探针见
`java/src/main/java/com/xb/sgc/papererase/vlm/AuditProbe.java`（独立诊断入口，不参与交付流水线）。

复跑命令：

```bash
cd java && JAVA_HOME=/Library/Java/JavaVirtualMachines/jdk1.8.0_291.jdk/Contents/Home \
mvn -q exec:java -Dexec.mainClass=com.xb.sgc.papererase.vlm.AuditProbe \
  -Dexec.args="<skillRoot> --cases /tmp/audit_synth 3"
```

| 样本 | 类型 | 3 轮 body_changed | 判定 |
| --- | --- | --- | --- |
| cut2（框边切正文 2 像素） | 阳性 | false×3 | **漏报** |
| cut5（切 5 像素） | 阳性 | false×3 | **漏报** |
| cut10（切 10 像素） | 阳性 | true×3 | 命中 |
| cut20（切 20 像素） | 阳性 | true×3 | 命中 |
| chardelete（框外整字被涂掉） | 阳性 | true×3 | 命中 |
| linedelete（紧邻框正文整行消失） | 阳性 | true×3 | 命中 |
| fardamage（页面中部正文行消失，远离框） | 阳性 | true×3 | 命中 |
| clean（只擦页码） | 阴性 | false×3 | 正确 |
| ghostonly（页码浅灰残影） | 阴性 | false×3 | 正确 |

**结论**：阳性 7 例命中 5 例（71.4%），阴性 2 例零误报。
识别门槛在 **10 像素左右**：≥10px 的切口稳定命中，≤5px 稳定漏报。
漏报样本的 evidence 显示模型确实检查了框边，但把 2-5 像素的切口看成"边缘位于正文行下方空白处"——
这是空间分辨能力的下限，不是提示词措辞问题。缩小缺口需要提高 ROI 分辨率或改用像素级判据（属 Java 侧改动，暂不采纳）。

### 提示词加固尝试记录（2026-09-18，均未冻结）

针对 ≤5 像素切口，按"先草稿、验证通过再冻结"的流程试了三版提示词，样本为 cut2 / cut5（阳性）+
clean / ghostonly（阴性），每版每样本 3 轮：

| 提示词 | 改动思路 | cut2 | cut5 | 阴性对照 | 是否冻结 |
| --- | --- | --- | --- | --- | --- |
| `audit-prompt-v13.md`（基线） | 逐边检查 + 框边穿过正文行 | false×3 | false×3 | 全部正确 | 当前生效 |
| `drafts/audit-inside-check.md` | 改判据：看"涂白区域在 ORIGINAL 中是否含正文笔画" | false×3 | false×3 | 全部正确 | 否，无收益 |
| `drafts/audit-touch-is-damage.md` | 改判据：只看框边与正文"有没有肉眼可见空白间隔"，并明确"文字仍可读不算安全" | false×3 | false×3 | 全部正确 | 否，无收益 |

**实验结论**：三版提示词的 evidence 都显示模型**正确注意到**了框边位置（草稿 C 甚至写着"框边与上方正文行之间有明显空白间隔"），
但实际是框切进了正文行 2-5 像素——模型把被切掉的字底当成了正常留白。
也就是说，2-5 像素级的差异已经低于模型对该 ROI 的空间分辨力，**换判据措辞无法解决，继续调提示词没有收益**。
草稿保留在 `drafts/` 作为实验证据，不进入版本号序列；正式链路仍是 `audit-prompt-v13.md`。
若要覆盖这一档，只能走输入侧（放大 audit 的 ROI）或像素级判据，两者都属 Java 侧改动，当前不采纳。

### audit ROI 放大 3 倍（2026-09-18，Java 侧输入改动，已生效）

背景：上节结论"只能走输入侧"，于是按"先临时脚本验证、稳定后再改代码"的流程做了实验。
探针 `AuditProbe` 加 `roiScale` 参数，对同一批合成样本做 1x / 2x / 3x 对照（每档 3 轮）：

| 倍率 | cut2（阳性） | cut5（阳性） | cut10（阳性） | clean（阴性） | ghostonly（阴性） |
| --- | --- | --- | --- | --- | --- |
| 1x | false×3 | false×3 | true×3 | false×3 | false×3 |
| 2x | false×3 | false×3 | true×3 | false×3 | false×3 |
| 3x | false×3 | **true×3** | true×3 | false×3 | false×3 |

3x 追加 5 轮确认：cut5 命中 5/5（累计 8/8），cut2 仍 0/5，两个阴性对照 0 误报。
据此改代码：`ExamPipeline` 新增 `AUDIT_ROI_SCALE = 3`，`auditRois` 与诊断审计的 ROI
**原图与擦除图同倍率放大**（整页图不动，仍按 `max_preview_long_edge` 走）。

代价与配套：ROI 放大后单页输入 token 变多，v13 的长 evidence 在宽框页面被截断
（协议报错 4/12），因此配套出了 v14（短 evidence）。两者合起来：
cut5 识别 5/5、截断 0/12、阴性零误报。

仍未覆盖：**2 像素级切口**（cut2 在 1x/2x/3x 全部漏报），需更高倍率或像素级判据，暂不做。
